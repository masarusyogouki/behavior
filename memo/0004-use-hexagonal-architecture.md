# 機能単位のモジュールとヘキサゴナルアーキテクチャを採用する

- ステータス: 採用
- 対象: Webの環境管理、Workerの遠隔セッション制御、共有通信契約
- 関連: [構想メモ #7](https://github.com/masarusyogouki/behavior/issues/7)、[TypeScript](0001-use-typescript.md)、[Next.js](0002-use-nextjs.md)、[VNC](0003-use-vnc-for-screen-streaming.md)

## 背景

現在はWeb画面からGitHub ActionsのWorkerを起動し、WebSocketとVNCを介してブラウザーを操作する。クリックしたDOM・セレクタ候補を表示できる。

今後は次の機能を追加したい。

- 選択したDOMを使った入力・クリックなどによるテスト作成
- ブラウザー操作とAPIリクエストを組み合わせた実行計画
- CloudflareのSQLiteへのテスト定義の保存・編集・再実行（D1など、具体的な保存先は未確定）
- GitHub ActionsのWorkerによる並列テスト実行
- ユーザー・料金プラン別の並列上限とキューによる待機制御
- Redisなどを使った実行枠の管理（採用製品は未確定）

環境サービスにはGitHubのrun・artifact・stepの仕様と製品の起動ルールが同居していた。WorkerのWebSocketサーバーはPlaywrightとVNCを直接生成し、起動・終了まで担当していた。UIとWorkerの通信型も別々に定義されていた。将来の実行ルールをこれらの外部仕様から分離する必要がある。

## 検討した案

| 案 | メリット | デメリット |
| --- | --- | --- |
| 現状維持 | 移行コストがなく、今の小さな構成を追いやすい。製品機能の検証に集中できる。 | 保存・課金制限・キューを追加すると、外部仕様と業務ルールの結合が強まる。実環境なしで起動失敗や状態遷移を検証しにくい。 |
| 機能単位のモジュールと一般的なレイヤー分割 | 機能の所在が明確で、少ない抽象化で実装できる。段階的に移行しやすい。 | サービスがGitHub・DB・Playwrightに直接依存する場合、複雑な実行ルールの検証や基盤交換が難しい。 |
| 機能単位のモジュールとヘキサゴナルアーキテクチャ | ユースケースを外部実装から独立させ、テスト用の実装に交換できる。保存先・起動基盤・ブラウザー実装の変更を限定できる。 | ポートや組み立て処理が増える。必要以上に細かい分割をすると理解しにくくなる。 |
| 独立サービスとイベント駆動 | 実行管理などを独立配置・拡張でき、大量実行や複数チーム開発に向く。 | 分散した状態の整合性、重複配信、監視、通信失敗への対応が増える。現在の規模では運用負担が大きい。 |

## 判断と理由

機能単位のモジュールに、ヘキサゴナルアーキテクチャを組み合わせる。中心のdomain/applicationがポートを定義し、外側のアダプターがそれを実装する。実行時の設定と具象実装はcomposition rootで組み立てる。

今後の中心は、環境起動だけでなく「テストを保存し、プランに従って実行する」という製品のルールになる。これをGitHub Actions、DB、Redis、Playwrightから独立して検証できることを重視した。一方、独立サービス化は必須にせず、WebとWorkerの既存の配置単位を保つ。

通信契約はReact・Node.js・Playwrightに依存しない共有ソースとする。現在は小規模なので専用パッケージの公開・ビルドやルートworkspaceへの移行は行わず、相対importで利用する。

すべてのファイルを形式的なdomain/application/adapterに分けない。現在存在するユースケースと、交換・検証する価値がある外部依存に境界を設ける。

## 今回の依存方向

```text
Next.js API（入力アダプター）
    ↓
EnvironmentService（アプリケーション）
    ↓ 利用するポート
EnvironmentProvisioner / SessionTokenIssuer
    ↑ 実装
GitHubActionsProvisioner / JwtSessionTokenIssuer
```

```text
WebSocketサーバー（入力アダプター）
    ↓
RemoteSession（アプリケーション）
    ↓ 利用するポート
BrowserSession / DisplaySession
    ↑ 実装
PlaywrightSession / VncDisplay
```

- Webのcomposition rootは `web/src/server/environment-service.ts`。HTTPレスポンスへの変換はAPIルートに置く。
- Workerのcomposition rootは `worker/server.ts` と `worker/composition.ts`。Origin/JWT認証、ping/pong、VNC中継、プロセス終了はランタイムのアダプターに置く。
- `RemoteSession` は画面→ブラウザーの起動順序、操作の直列実行、起動失敗時の終了、切断途中の後片付けを管理する。
- `shared/contracts` はブラウザー操作・通知・環境APIの型を持つ。受信通知は形式を検証してからUIへ渡す。
- Reactの接続フックはブラウザー側のアダプター。表示用の `App.tsx` からAPIポーリング・WebSocket・noVNC・セッション保存を分離する。
- Playwrightに注入するページ内スクリプト、JWTの暗号処理、DNS検査、OSプロセス操作は外側に閉じ込める。
- 依存方向は `tests/architecture.test.ts` で検証する。

## 保持する動作と制約

APIパス・レスポンス、WebSocketのメッセージとサブプロトコル、VNCの一時トークン、JWT再利用拒否、Originと通信先の制限を維持する。

現在の全体で1環境という起動ルールとworkflowのconcurrency groupは変更しない。`hasActiveEnvironment` と `start` は原子的ではなく、今回のポート分離だけで分散した並列制限が完成するわけではない。将来は実行要求・枠の確保・キュー・状態照合の設計とともに置き換える。

通常切断ではブラウザーと画面を終了し、Workerプロセスは既定10分間再接続を待つ。ブラウザー内容を保持したまま再接続する機能ではない。明示切断ではWorkerを終了する。

## 今後の拡張

今回、D1・Redis・キュー・自動実行・料金プラン管理は実装しない。将来は別の機能モジュールとして追加する。

- テスト定義は製品独自の構造化した操作形式にする。DOMやPlaywrightコード文字列をそのまま実行計画の中心にしない。
- 編集用遠隔セッションと自動実行ジョブは別ユースケースにする。
- 保存先へのポート、実行要求・結果のポート、実行枠やキューへのポートは、具体的なユースケースが決まってから追加する。
- 編集中の定義と実行時に固定するバージョン、実行要求と再試行を区別する。
- プラン別・全体・GitHub側の上限、起動要求済みと実行中の区別、取消・異常終了・通知漏れ・実行枠の回収を設計する。
- キューと実行枠の原子的な確保は別の責務として扱う。

## 見直す条件

- 具体的なユースケースに対して、ポートと実装の受け渡しだけの層が増えた場合は境界を簡素化する。
- 実行量・運用・チームの分担によって独立配置が必要になった場合は、実行制御のサービス化を検討する。
- 共有通信契約が増えてバージョン管理や別リポジトリでの利用が必要になった場合は、パッケージ化を検討する。
