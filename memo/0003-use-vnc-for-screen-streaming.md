# Worker の画面配信に VNC を採用する

- ステータス: 採用
- 対象: Worker から Web UI へのリアルタイムな画面配信

## 背景

Worker 上で動くブラウザーの画面を、Web UI にリアルタイムで表示する必要がある。

当初は、Worker が JPEG スクリーンショットを毎秒60枚取得し、WebSocket で送信する方式を採用していた。

## JPEG を WebSocket で送る方式の問題

60 FPS で配信しても、操作に対する画面の遅延を感じた。

また、画面に大きな変化がなくても一定間隔でスクリーンショットの取得とJPEGへの変換を続けるため、環境を起動して接続しているだけでCPUを約1コア使用した。接続数が増えることを考えると、この常時負荷は許容しにくい。

この問題はWebSocket自体ではなく、画面全体を一定間隔でキャプチャしてJPEGとして送る方式によるものと考えた。

## 検討した選択肢

### WebRTC

JPEGを連続送信する方式よりも低遅延な画面配信を期待でき、体感上のラグを減らせる可能性があると考えた。

一方で、映像のエンコードなどによりCPU使用率が高くなることが予想された。WorkerのCPU負荷を抑えるという要件に合わない可能性が高いため、採用しなかった。

なお、このCPU負荷は実測結果ではなく、検討時点での予想に基づく判断である。

### VNC

VNCはAIから提案されたことをきっかけに検証した。

実際に試したところ、JPEGを60 FPSで送る方式と比べて、操作時にラグを感じる場面が減った。また、CPU使用量は次の程度だった。

- 画面を起動し、変化がない状態: 約0.01コア
- 画面全体が切り替わる状態: 約1.3コア

画面に変化がないときのCPU負荷が非常に小さく、画面全体が変化したときだけ一時的に負荷が上がる。常に約1コアを使用していた従来方式よりも、Workerのリソースを効率よく利用できる。

## 判断

Workerの画面配信にはVNCを採用する。

現在は、Worker上のx11vncから画面を取得し、VNC通信をWebSocketで中継して、Web UIのnoVNCで表示する。操作命令などに使用するWebSocketも引き続き利用する。

採用理由は、従来のJPEG配信よりも体感上の遅延が小さく、画面に変化がないときのCPU使用量を大幅に抑えられたためである。

## 測定値について

CPU使用量は検証時の環境で観測した概算値であり、Workerに割り当てたCPU、画面サイズ、更新内容などによって変化する。将来比較する場合は、同じ条件で改めて測定する。

## 見直す条件

次のような状況になった場合は、画面配信方式を改めて検討する。

- VNCの遅延や画質が製品要件を満たさなくなった場合
- 同時接続数を増やしたときに、VNCのCPU使用量や通信量が問題になった場合
- WebRTCなどの方式について、実際の環境でVNCより優れた測定結果が得られた場合
